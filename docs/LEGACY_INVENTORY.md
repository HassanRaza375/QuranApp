**Check result (Phase 0, amendment 2):**
- All three upstreams answer with `Access-Control-Allow-Origin: *` (checked with a cross-origin request). `api.aladhan.com` also sends it, after a 302 to the month-path form.
- No file in the legacy `app/` calls `/api/chapters`, `/api/surahs`, `/api/sajda` or `/api/juz`. The proxies are present but **unused**.
- None of them is needed for CORS. The only logic is the `juz` regrouping and input check.
- Decision taken: the four are kept, copied into `revamp-quran/server/api`, because the build is `nuxt build` (Nitro) and the proxies cost nothing. Two lint fixes in the copies: `catch {` instead of an unused `e`, and `await` added in `chapters.get.js` (the legacy `try/catch` never caught a failure because the fetch was not awaited). **Open question for you:** drop them at cutover, since nothing uses them?

### Other stores

- **IndexedDB** `quran-app-db` version 1: object stores `chapters` and `tafsirs`, key = surah number (`useQuranDB`).
- **Cache Storage:** `workbox-precache-*`, `quran-api-cache`, `quran-audio-cache`, `quran-downloads-audio-cache`, `wajibat-data-cache`.
- **Cookie:** `theme-resolved` (legacy SSR only; not needed by the SPA).

## "Clear all data" and "Export" (legacy Settings page), exactly

- **Clear all data** runs `localStorage.clear()` and then `location.reload()`. So it removes **every localStorage key of the origin** (the whole table above, including keys this inventory may have missed).
- It does **not** touch: IndexedDB (`quran-app-db`), Cache Storage (all caches above, including downloaded audio), the `theme-resolved` cookie, or the service worker.
- Side effect to be aware of: `quran:downloads:v1` is wiped while the downloaded audio stays in Cache Storage, so the Downloads page shows nothing and the storage is not freed.
- **Export** dumps every localStorage key to a JSON file (parsed when valid JSON, raw otherwise). IndexedDB and Cache Storage are not included.
- The revamp does **not** extend either behaviour in Phase 0 (rule from the Phase 0 approval). Settings (Phase 2) will recreate them exactly as above.

## The legacy Settings page (read in Phase 2)

- One scrolling page of cards (theme, fiqh and location, notifications, reading, audio, accessibility, modules, data), not sections. It also holds the Daily Fiqh marja' picker (Ja'fari only, `quran:fiqh-prefs:v1`).
- **Export** (`exportData`): every localStorage key, JSON parsed when valid and raw otherwise, in `quran-app-data-<date>.json`; the date is the UTC date. Not IndexedDB, not Cache Storage. No import.
- **Clear all** (`clearAllData`): `localStorage.clear()` then `location.reload()` after a confirmation dialog. Leaves IndexedDB `quran-app-db`, Cache Storage (including downloaded audio), the `theme-resolved` cookie and the service worker.
- **Notifications:** `prayerSettings` = `{ notificationsEnabled, enabledPrayers: {Fajr..Isha}, reminderOffset (minutes: 0, 5, 10 offered) }`. Turning the switch on calls `Notification.requestPermission()`; a refusal shows `alert()`. Reminders are `setTimeout` timers in the open page (`scheduleNotifications`) that call `registration.showNotification`. There is no push handler, background sync or notification code in the service worker, so **nothing arrives while the app is closed**; the page says so. Timers use the device-local `setHours` on today's times and roll today's time forward for tomorrow.
- `layouts/default.vue` calls `prayer.init()` on every page, which also asks the browser for the device location as soon as the app opens, and falls back **silently to Lahore** if it is refused or unavailable (a small line in Settings says so).
- The legacy Settings has no Reset and no Asr, method, Hijri, Wi-Fi or verse-layout settings; it writes `preferredVerseDisplay` (which text the reader shows) from its "Default verse display" and the reader's tabs.

## The legacy Surah reader (read in Phase 4A)

- **Data:** `GET quranapi.pages.dev/api/<n>.json` has the names, place, ayah count, five `audio` entries and five texts of the same length (`arabic1` with marks, `arabic2` plain, `english`, `urdu`, `bengali`); Al-Baqarah is 527 KB. Tafsir is one request per ayah, `/api/tafsir/<s>_<a>.json`, with `tafsirs: [{ author, groupVerse, content }]` for Ibn Kathir, Maarif Ul Quran and Tazkirul Quran (a `groupVerse` note can come with any of them; the largest seen was 51 KB). The content is markdown-lite, rendered by `renderTafsirMarkdown` (escape first).
- **Cache:** IndexedDB `quran-app-db` (`chapters`, `tafsirs`), then the service worker's `quran-api-cache`. The revamp never opens `quran-app-db`.
- **Display:** a text tab (`preferredVerseDisplay`) replaces the Arabic with another text; a per-ayah Translation panel (choosing sets `translationDefaultLang`) and a per-ayah Tafsir panel (choosing sets `tafsirDefaultAuthor`). The Tafsir picker said "Sunni sources, no Shia/Ja'fari tafsir is available from this app's data provider".
- **No bismillah** is shown (the data has it only as ayah 1 of surah 1; no other surah's first ayah repeats it, checked for all 114). **No pin** exists. The Save star had no Undo.
- **`#ayah-N` links** (Home, Library, Goals) are produced everywhere but nothing scrolls to the hash after the async load.
- **Progress:** a scroll listener (400 ms) writes the last ayah above 35% of the screen to `quran:reading-progress:v1` (`surahName` is the English meaning, `surahNameArabic` the long Arabic name); ayah 1 is skipped. Each tracked ayah also appends `"<s>:<a>"` to `quran:reading-goals:v1` `dailyLog[<local day>]`, only the ayah the pause landed on, so a steady scroll logs almost nothing.
- Per-ayah audio always used reciter 1's file (`verse.audio["1"]`).

## `ayah-of-day`: two legacy bugs (found in Phase 1)

- **UTC date.** `useAyahOfTheDay` stores `{ date: new Date().toISOString().slice(0, 10), data }` and compares the stored `date` with the same UTC date. The ayah therefore changes at UTC midnight, not at the user's midnight: at 05:00 local time in Pakistan (UTC+5), in the evening in the US. From local midnight to 05:00 in UTC+5 the app still treats yesterday as today.
- **Invalid ayahs.** The pick is `surah = random 1 to 114`, `ayah = random 1 to 7`. For surahs with fewer than 7 ayahs this asks for an ayah that does not exist (for example ayah 4 to 7 of surah 108, which has 3); the request fails and the card stays empty. 11 of the 114 surahs have fewer than 7 ayahs, so about 3.5% of picks (28 of the 798 surah and ayah combinations) are invalid and show nothing.
- Stored `data` fields the legacy component reads: `arabic`, `translation` (English), `urdu`, `surah_name` (the long Arabic name), `ayah_number`, `surah_number`. It shows the Urdu translation, not the user's chosen language.
- **Revamp fix** (`app/lib/ayahOfDay.ts`): same key and shape; `date` stays the UTC date so the legacy comparison keeps working; an additive `localDate` (local calendar day) decides "today" in the revamp; the pick is deterministic from the local date and only valid, in-range ayahs. See `docs/phases/phase-01-home.md`.

## How the legacy reader uses the three reading keys

| Key | Meaning in the legacy app |
| --- | --- |
| `preferredVerseDisplay` | Which **single text** the whole Surah reader shows as its verse line: a tab strip of `arabic1`, `arabic2`, `english`, `bengali`, `urdu`. Read on mount of `/surah/[id]` (validated against that list), written when the user taps a tab, and also editable in Settings under "Default verse text". It is not a layout (it does not control Arabic-first vs Translation-first). Left untouched; a new `quran:verse-layout:v1` is added later for the prototype's Arabic-first / Translation-first choice. |
| `translationDefaultLang` | The **last language picked** in the per-ayah inline translation panel (`english`, `urdu`, `bengali`, `arabic2`). Written every time a language is chosen in the reader or in the Prophets & Persons `AyahReferenceCard`; used as the pre-selected language when the next panel opens. Settings does not expose it. |
| `tafsirDefaultAuthor` | The Tafsir source (`Ibn Kathir`, `Maarif Ul Quran`, `Tazkirul Quran`) pre-selected for the per-ayah tafsir panel. Written when a source is picked in the reader or `AyahReferenceCard`, and settable (or clearable) in Settings; shared by both places. |

In the revamp's preferences store these map to `verseDisplay`, `translationLang` and `tafsirAuthor`, with the same keys and raw formats.

**Legacy prayer code (found in Phase 1):** `stores/prayer.js` reads times with `split(":").map(Number)`. The daily endpoint returns `"04:59"`, but the monthly endpoint returns `"04:59 (PKT)"`, whose minutes become `NaN` with that code, so the legacy parser cannot be reused on the monthly data (the revamp parses with a regex and tests both formats). The legacy store also falls back silently to Lahore when location is unavailable, and keys its cache per day and exact coordinates.

**Observation on the legacy bug G6 (not fixed, logged separately):** the legacy `dist/sw.js` calls `createHandlerBoundToURL("/")` but its precache list has no `/` entry (the legacy app is server-rendered, so there is no `index.html`). Workbox throws `non-precached-url` when the worker script is evaluated, so every `registerRoute` after that line (including the runtime caching rules) is likely never registered. This is the probable root cause of the offline-new-tab failure. It was read from the repo's built `dist/`, which may be older than the deployed build, so verify on the deployed worker before relying on it. The revamp precaches `/` (the SPA shell), and `e2e/offline.spec.ts` proves a new tab opened offline at a deep route renders.
